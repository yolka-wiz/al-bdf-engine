# CONTRIBUTING.md — albdf contribution rules

> These are the binding rules for every contributor — human or AI agent.
> The short version is also summarized in `REPO_MAP.md`; this file is the
> full contract. If a task conflicts with these rules, STOP and ask the
> orchestrator rather than improvising.

## 1. Branch per task; commit each major step

- **Create a branch** for every task/milestone: `m<milestone>/<slug>` or
  `fix/<problem>` (e.g. `m8.1/p3-vertical-mark-offsets`).
- **Commit each major step** as you go — one logical change per commit,
  Conventional Commits format: `feat:`, `fix:`, `test:`, `docs:`,
  `refactor:`, `chore:`.
- Commit messages explain **WHY**, not just what.
- Every commit must compile — no "wip" commits that break the build. Use
  `git stash` or work on the branch instead.
- Merge via rebase; keep history linear. Squash only under explicit
  instruction.

## 2. Update docs about what you change, as you change it

Document as you go — docs written after the fact drift.

| You changed... | Update |
|---|---|
| Component status, a task, a decision | tracking DB: `python3 scripts/db.py ...` |
| A design/project decision | an ADR in `docs/decisions/` + a DB row |
| A known limitation / a bug you fixed or introduced | `docs/PROBLEMS.md` |
| CLI behavior or a command | man page `docs/albdf.1` (+ README if it lists commands) |
| A shipped release | `docs/RELEASES.md` |
| Code rules (style, tests, git workflow) | `docs/coding-standard.md` |
| Anything structural | `REPO_MAP.md` is regenerated by the pre-commit hook |

**Markdown structure rule:** every markdown file except `README.md` must be
**structured** — an H1 title, clear section headings, a real body. Not a
minimal stub. The pre-commit hook enforces the mechanical part (H1, ≥2
headings, non-trivial body) on staged files; keep the *logical* structure
(headings that match content, tables for comparisons, decisions recorded with
context) as the human/agent standard.

## 3. Do not push to main until fully tested

- Work happens on branches. **Never push straight to main.** The only
  exception is an emergency hotfix, and even then it must go through a
  review immediately after.
- Before merging to main, the full gate must be green:
  ```bash
  bash ci/run-ci.sh        # Release build + ctest + ASAN/UBSAN + clang-format
  ```
- Plus, for behavior changes: the CLI smoke suite
  `QT_QPA_PLATFORM=offscreen bash src/tests/smoke.sh ...` and any
  golden-image/round-trip checks affected by the change.
- TDD applies: every bug fix gets a failing test first; every feature gets
  tests that fail before the feature lands.
- The orchestrator (or a reviewer) verifies claims — never mark a task done
  without a real `git log` + passing test as evidence.

## 3b. Pushing & merging — hard rules

- **Protected branch:** `main` is protected (see `docs/branch-protection.md`).
  Direct pushes are rejected by the remote; changes land only via PR + review
  + green CI.
- **PR checklist** (required for every pull request):
  1. Branch off the latest `main`; rebase before opening.
  2. Title/description in Conventional Commits style; link the task (DB #).
  3. `ci/run-ci.sh` green (or the hosted CI job green) on your branch.
  4. Docs updated (`PROBLEMS.md`, man page, ADR, DB — as applicable).
  5. **No secrets** in the diff — the pre-commit hook scans; the hosted CI
     re-scans. A secret that was ever pushed must be rotated, not just
     deleted from the branch.
  6. At least one review approval from someone who did not write the change.
- **Force-push policy:** `--force-with-lease` only, and only on your own
  feature branch. Never force-push `main`. History rewrites require the
  orchestrator's explicit sign-off (used for secret scrubbing).
- **Merge strategy:** rebase-merge to keep history linear; squash only on
  explicit instruction.

## 4. Update the problem list your code change made

- If your change **fixes** a known problem (P1–P6, R#1–R#3, S#1–S#2, or a new
  one), update the `docs/PROBLEMS.md` entry: mark it **Fixed** with the commit
  sha, and note the root cause + workaround history.
- If your change **creates** a problem or degrades a documented workaround,
  ADD a new entry immediately — do not leave the sharp edge undocumented.
- Record the same in the tracking DB (`db.py task-done <id> --ref <sha>` or a
  new task/note) so the DB stays the source of truth.

## 5. Do not upload unnecessary files, secrets, or data

- **No secrets**: no API keys, tokens, passwords, certs, or connection
  strings in any committed file — not even redacted-looking ones. A public
  repo is scraped within minutes; rotate anything that was ever pushed.
  Runtime config (Hermes config, env, keyrings) lives outside the repo.
- **No junk**: no build artifacts (`build/`, `*.o`), editor droppings,
  logs, large binaries, or local scratch data. `.gitignore` covers the known
  set — if you generate a new artifact class, extend `.gitignore` rather than
  fighting it.
- **No user data**: real-world documents (e.g. `testing-temp/`) stay OUT of
  the repo; fixtures are OFL-only and committed deliberately.
- **No unnecessary files**: don't commit scaffolding, backups, or files
  unrelated to the change. Review `git status` before committing.
- If you ever discover a secret was pushed, tell the orchestrator
  immediately — purge with `git-filter-repo` and rotate the credential. Do
  not silently rewrite history.

## How the pre-commit hook works

`scripts/install-hooks.sh` sets `core.hooksPath=.githooks`. On every commit,
`.githooks/pre-commit`:

1. regenerates `REPO_MAP.md` from the tree and stages it, and
2. runs `scripts/check-markdown-structure.py` on staged `.md` files
   (README.md and vendored `skills/` are exempt).

If you must bypass (emergency fix on a doc mid-edit), use
`git commit --no-verify` — but the gate runs in `ci/run-ci.sh` anyway, so
bypassing only delays the check.
